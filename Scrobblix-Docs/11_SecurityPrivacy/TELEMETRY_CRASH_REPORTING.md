# Telemetry and Crash Reporting — Current State and Policy

> **Project:** Scrobblix  
> **Owner:** Rahul Muraleedharan (`frpboy`)  
> **Status:** Local diagnostics by default; optional build-time automatic crash reporting added 2026-11-15 (owner-directed, minimal scope); no shipped release contains it, and regular release builds reviewed so far are not activated (isolated synthetic config tests are separate)  
> **Last reviewed:** 2026-11-16  
> **Review note:** the public privacy-notice wording for this change is drafted below (coordinated legal/review draft) and still requires owner review before any release that ships it.

## Current default behavior

Scrobblix uses a local-first design. No shipped Scrobblix release (through Android 0.1.0-alpha.2 and the current Windows previews) establishes a Scrobblix-operated telemetry endpoint, remote usage analytics dashboard, automatic crash-report upload, or third-party crash SDK. The current source on main adds an optional build-time crash-reporting candidate (see below) that no shipped release contains and that current builds do not activate: the regular release builds reviewed so far bake an empty DSN; isolated synthetic test configurations are separate. The local-only baseline is kept. A source-level capability is not a shipped behavior. Local diagnostic logs and support exports are not automatically uploaded. Listening metadata used for Last.fm authorisation, Now Playing and scrobbling follows the platform-specific network behavior described in the privacy policy.

Do not describe a telemetry toggle or automatic crash-reporting preference as a shipped UI control unless the exact release contains it.

## Current local diagnostics

The app records minimized operational logs and shows source/queue/provider/storage statuses in the local Diagnostics UI. The support exporter builds a user-initiated, allow-listed ZIP with a versioned manifest, summarized event counts, sanitized operational events and README. It excludes the listening database, credentials, artwork and arbitrary/free-form log messages by design.

The export is not automatically uploaded. Real Windows Save/cancel behavior, seeded-canary redaction, ZIP content review and accessibility remain qualification gates.

## Future opt-in telemetry requirements

Any future telemetry proposal requires a separate data map and architecture decision before implementation:
- purposes and user benefit clearly explained;
- field-level schema and examples;
- recipient/endpoint, transport and access controls;
- consent and revocation UX;
- retention and deletion behavior;
- exclusion of listening history, titles/artists/albums, full URLs, usernames, credentials and cross-product identifiers unless a separately reviewed explicit opt-in is approved;
- tests for minimization/redaction and accidental upload prevention;
- updated privacy notice, release disclosure and support documentation.

Prefer aggregate reliability counters that cannot reconstruct listening patterns. Do not introduce advertising identifiers, cross-app tracking or telemetry merely as an incidental dependency.

## Crash reporting

Crashes may be diagnosed from local event logs and Windows Application events. Raw dumps can contain secrets, listening history and memory contents; they are not included in the support bundle by default.

### Optional automatic crash reporting (build-time, added 2026-11-15)

On 2026-11-15 the owner directed minimal automatic crash/error reporting across his apps. Scrobblix implements it as a build-time option on both Android and Windows: a release built with the public Sentry ingest DSN reports unhandled exceptions; a build without the DSN keeps the local-only baseline above. The DSN is a public write-only ingest identifier, not a credential. On Windows the DSN reaches the code through generated source (SCROBBLIX_SENTRY_DSN environment variable baked into ScrobblixSentryDsn.g.cs at build time); on Android through BuildConfig. The Windows value is validated as an exact Sentry HTTPS ingest DSN shape before it is baked in, and CI builds with a synthetic DSN in an isolated artifacts layout and reads the compiled constant back through reflection (no Sentry init), so an empty-DSN green build can never masquerade as a wired one; a second isolated empty-DSN build proves no synthetic value is reused.

What a report contains, deliberately minimal:
- a fresh event id and timestamp, the app release and platform, and a fixed exception type/value constant (ScrobblixGenericCrash) meaning "an unhandled error occurred";
- no content derived from the captured exception, the device, the user or the SDK pipeline survives the rebuild: no exception type names (type names are input-derived too), no exception messages, no stack frames, threads, mechanism, contexts, tags, extras, breadcrumbs, request or user data, and no original or SDK envelope headers (no trace context). The wire does carry code-owned or SDK-default structural fields, observed per platform: Android emits an empty contexts object; Windows emits an empty sdk object, platform csharp, and a sent_at in the envelope header;
- the event says only: this app version on this platform reported an unhandled error. Because the boundary rewrites event ids, remote receipt verification for tests is an exact lookup of the FINAL wire event id - captured privately per attempt - plus its timestamp, done by the Sentry project owner; timestamp correlation or echoed content alone never counts as receipt.
- outbound HTTP headers, observed on the actual wire per platform (verified against captures of the production transport, not field assignments). Android sends exactly: User-Agent (fixed generic scrobblix-boundary/1 in place of the platform default, which would carry OS and device-build metadata), Content-Type: application/x-sentry-envelope, code-owned X-Sentry-Auth, Content-Length, Host, Connection, Accept-Encoding: gzip. Windows sends exactly: Host, code-owned X-Sentry-Auth, Transfer-Encoding: chunked, Accept-Encoding: gzip, deflate - no User-Agent and no Content-Type. Neither sends cookies or device-derived headers.

Enforcement is two-layer on both platforms:
1. a beforeSend filter (CrashEventFilter on Android, CrashReporting.ApplyPrivacyBoundary on Windows) strips every event carrier - request, user, breadcrumbs, message, tags, extras, all contexts and frame absolute paths - and clears the hint-level carriers that bypass event field mutation (attachments, screenshot, view hierarchy, thread dump, tombstone). This is defense-in-depth only;
2. the authoritative final transport gate (EnvelopeGate + FilteringEnvelopeTransport on Android, FilteringEnvelopeTransport on Windows), independent of every hook: whatever envelope reaches the wire is REBUILT from code-owned constants with a fresh event id and timestamp. Original envelope bytes and original event items are never retained. Non-event envelopes (sessions, client reports, replays) are dropped entirely. Context-name allowlists were rejected as insufficient: the boundary owns the whole event, it does not filter fields.

Both layers are proven by tests that serialize the actual SDK envelope: hostile payloads are injected through every carrier, through a direct scope/attachment bypass attempt against a real SentryClient, and through a hand-built custom envelope straight at the gate; the Windows test drives the production transport against a recording HTTP handler and asserts on the actual request bytes, and the Android test drives the production transport's real blocking POST against a loopback server and asserts on the actual wire body after a deliberately discarded event. Asserted: the outbound event is the generic constants-only report, input exception types and stack frames never cross, fresh event ids replace hostile ones, no client_report item is emitted, send bursts collapse under the attempt budget, and no injected string survives.

Platform SDK hardening, explicit at init:
- Android: NDK/native crash capture, scope sync, ANR, auto session tracking, activity lifecycle breadcrumbs and all auto breadcrumbs are disabled; manual SentryAndroid.init (not the manifest provider) so these overrides cannot be bypassed;
- Windows: capture is the SDK default chain (AppDomain unhandled exceptions, unobserved task exceptions) with no custom duplicate handlers; HTTP redirects are disabled so a hostile or misconfigured endpoint can never bounce the payload;
- both: no performance traces, no session replay, no screenshots; sendDefaultPii is false and no user, account or IP-identifying field is ever attached; listening history, track/artist/album metadata, queue contents, artwork, exported logs and credentials are never attached to events; manual local logs and the user-initiated support ZIP remain unchanged;
- client reports are off on both platforms (init flag; on Android the direct synchronous worker transport has no attach point at all). The actual downstream wire is tested on loopback after a deliberately discarded event: no client_report item appears.

Delivery bounds, deliberate: delivery is best-effort with no guarantee of crash delivery. Bounds are process-local hygiene (they reset on restart): within a process a crash loop cannot become a network or quota loop - at most one send in flight, a minimum interval between attempts and a hard per-process attempt cap (Windows also sets MaxQueueItems=1); a send failure or budget excess drops the report instead of retrying. Crash reports are never persisted to disk: Android uses a dedicated no-op envelope cache (deliberately not the SDK sentinel, which the Android initializer would replace with the on-disk cache) with no cache directory; Windows configures no cache directory. Tests verify the no-op cache survives SDK init and that no cache files are written. The Android transport rebuilds and serializes the generic event before any handoff, then posts the fixed bytes on a single bounded worker (never on the capture caller, which can be the main thread): the send budget is held for the whole actual exchange including cleanup (never merely an enqueue), redirects are off, the body is posted with a fixed length (a buffered POST is never transparently replayed after a connection loss), server rate-limit headers (X-Sentry-Rate-Limits, X-Sentry-Rate-Limit, Retry-After in delta-seconds, fractional or HTTP-date form, on any status; the longest window wins, truncated to one hour, with a one-minute 429 floor) feed a cooldown, and the response body is drained with a fixed byte cap. Framing differs by platform: Android posts with an explicit fixed length, while Windows uses the pinned Sentry SDK's own request construction, whose envelope content cannot pre-compute its length - the actual Windows wire carries HTTP chunked transfer coding instead of Content-Length (observed in loopback wire captures of the real transport). Connect and read timeouts bound those phases only: DNS resolution and request writes use the JVM/socket defaults and there is no whole-request deadline, so a permanently stuck exchange holds its budget slot until the worker actually returns - potentially for the process lifetime, with later sends dropped rather than queued. The original crash flush latch is marked only after a 2xx response (acceptance at the HTTP layer, matching the SDK's own transport semantics, not a server-side storage receipt) - never on enqueue, cache or failure. The debug diagnostic carries per-attempt correlation, so it reports only its own attempt's wire event id, and it waits off the UI thread with a bounded wait. On Windows the same per-attempt correlation is keyed by the original (never-sent) event id and the diagnostic awaits the flush asynchronously.

Debug-only validation: debug builds expose "Send synthetic test crash report" (Settings on Android, Diagnostics on Windows). It queues one synthetic exception through the same boundary and reports the resulting wire event id; the result wording is deliberately "attempted", never "sent", and receipt counts only when the remote project shows that exact event id. Safe by construction: the generic gate leaves no real exception content behind, so no real crash has to be induced. It never appears in release builds, and it is not signed-release or unhandled-path proof - that remains the separately held ingest test.

Open follow-ups before any release ships this: public privacy-notice wording (owner review; coordinated DRAFT below), an isolated synthetic ingest test (at most one event per platform, test-only artifacts, no user devices) proving the generic event arrives and is verified by exact final wire event id plus timestamp, then signed-artifact unhandled-path qualification on real devices, and free-tier capacity confirmation (no paid plan).

DRAFT public privacy-notice wording (PENDING OWNER REVIEW - not approved for publication; coordinated legal/review draft, 2026-11-16):

> Some releases include automatic error reporting to Sentry. Whether it is enabled is set when that release is built; there is no in-app switch. When enabled, a report contains a newly generated event ID, a time, the app release and platform, and a fixed generic error label. The reviewed report format does not include the original error message or stack trace, listening history, track details, account names, credentials or support files. Sentry also receives ordinary connection information, including the connecting IP address. The current organisation settings are configured to prevent stored IP information and remove geographic fields, but that does not mean Sentry never processes the connection information. Sentry uses service providers to operate its service. Its documented default retention for error events on the current Developer plan is 30 days; this is not a deletion deadline for all app data or provider backups. If error reporting is disabled in a build, that reporting path does not send reports. Other network features, including Last.fm authorisation and automatic scrobbling, are described separately in the privacy policy. Local logs and any available manual support export are separate from automatic reporting.

Drafting rules carried with it: replace "Some releases" with the specific release's verified enabled/disabled state in its final notice (build configuration is not an end-user opt-in); never say "nothing leaves your device automatically" (other features use the network); never say "never shared further" (Sentry's service providers/subprocessors are involved); never claim a retention setting deletes all logs or backups; never say "no identifiers" (a random event ID is present and connection metadata is processed); describe an error signal rather than guaranteeing every report represents a process exit. Payload exclusions remain subject to final independent egress qualification on the exact signed artifact, not inferred from documentation.

## Qualification and release

Do not mark a telemetry/crash privacy test complete from docs or a successful build. Validate the exact release configuration and network behavior, including that no unauthorized outbound data is emitted.
